# Read ZCode quota through the bigmodel monitor endpoint

Treat ZCode coding-plan capacity as readable only through the same monitor endpoint the ZCode client itself uses: `GET {providerOrigin}/api/monitor/usage/quota/limit` with the coding-plan API key sent as the raw `Authorization` header. Discover the key and origin by reading `~/.zcode/v2/config.json`, selecting the enabled coding-plan provider (`enabled` with no `systemDisabledReason`); never prompt the user, never write back to ZCode state, and never persist or log the key. The key reaches the outbound `curl.exe` call through a stdin config file so it never appears in a process command line. Environment overrides (`ZCODE_BIGMODEL_USAGE_API_KEY`/`BIGMODEL_USAGE_API_KEY`, `ZCODE_BIGMODEL_USAGE_QUOTA_URL`/`BIGMODEL_USAGE_QUOTA_URL`) take precedence over the config file, mirroring the ZCode client's own override names.

The endpoint returns a dual-window array (`limits` with per-window `percentage`, credit counts, and `nextResetTime` in milliseconds) plus a plan `level`; windows are classified by reset time (earliest → five-hour slot, latest → weekly slot) rather than trusting the undocumented `unit`/`number` enum, and known `(unit, number)` combinations map to display durations. This keeps the failure surface small: an undocumented endpoint can change shape and the meter will surface a `CRV-5xx` diagnostic instead of guessing.

This widens ADR-0001's "Codex-only companion" scope (also recorded in PRODUCT.md) to a two-source meter: Codex capacity still flows exclusively through the `codex app-server` JSON-RPC session per ADR-0001, and ZCode quota flows exclusively through this monitor endpoint. The ADR-0001 prohibitions (no memory inspection, no stdio interception of the desktop app, no credential storage) apply to the ZCode path unchanged. Reading the plaintext quota key from ZCode's own config file is an explicit exception to "no credential scraping": it is used for a read-only GET and never leaves the machine except to its own provider origin.

ZCode reset cards are separate from quota and require `GET https://zcode.z.ai/api/v1/coding-plan/reset/status`, the same endpoint used by the installed ZCode client. To satisfy the user's request to display these cards, the reader additionally decrypts only the required existing login entries from ZCode's `credentials.json` in memory using its `enc:v1` AES-256-GCM format. The active provider's OAuth user ID selects the exact personal-account API key; that key must equal the key used for the quota response before the login tokens can be sent to the fixed official endpoint via curl stdin. Cached keys for other personal accounts and team keys cannot authorize this read. Tokens and user identities are never persisted, logged, refreshed or written back. No card claim/use or history mutation endpoints are called. Five-hour and weekly inventories are distinct, expired cards are excluded, and card failures carry separate diagnostics while valid quota remains available. Frontend polling reuses each pending source request so slow card reads cannot repeatedly invalidate successful quota responses.
